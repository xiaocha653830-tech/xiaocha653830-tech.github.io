## 语法合法，也可能已经变了意思

ETL-Agent 的 README 记录了一次质量分流异常：原本要拒绝特定姓氏的正则，在 Windows 提交链路中发生了字符替换。规则仍然能通过语法校验，作业也报告成功，但它检查的已经不是原来的条件。

这是一条文档记录的故障，不是本次重新执行得到的结果。代码中能确认的是：演示脚本已经把规则定义放在 Python 文件里，并增加提交后回读比较。

## 两条规则都能编译

问题可以用一个不涉及真实业务数据的小例子复现：

```python
import re

expected = r"^[^吴].*$"
changed = r"^[^?].*$"

print(bool(re.match(expected, "吴某")))  # False
print(bool(re.match(changed, "吴某")))   # True
print(len(expected.encode("utf-8")))    # 10
print(len(changed.encode("utf-8")))     # 8
```

第一条拒绝以“吴”开头的字符串，第二条拒绝以问号开头的字符串。两条规则语法都合法，业务含义却不同。

这解释了为什么“API 返回 200”“JSON 能解析”“任务状态为 succeeded”都不足以证明业务目标达成。每项检查覆盖的是不同层次。

## 提交后回读，把含义核对放在边界上

本地脚本读取响应中的 `quality_rules`，取出正则，与期望值逐字比较。若不同，则在继续流程前退出。

```python
# 从实际服务响应中读取已保存规则
stored = reply.json()["quality_rules"]
expected = DEMO_RULES[0]["params"]["pattern"]
actual = stored[0]["params"]["pattern"]

if actual != expected:
    raise ValueError("质量规则回读结果与提交内容不一致")
```

回读比较的价值在于它覆盖了序列化、传输、服务端处理和返回表示之间的一段边界。日志同时显示字符数与 UTF-8 字节数，可以帮助发现替换，但长度相等仍不代表内容相同，最终还是要比较值。

## 不要把编码问题一律归因给 JSON

字符可以在进入 JSON 序列化之前就被破坏。例如终端、管道、脚本文件与子进程使用不同编码时，替换可能已经发生。之后的 JSON 编码器只会忠实保存那个错误字符。

比较稳妥的做法是让结构化对象经客户端的 JSON 参数发送，减少手工拼接字符串与跨 shell 传递。对于关键规则，再加入回读和业务正反例校验。

`ensure_ascii=True` 与 `False` 控制的是序列化表示方式；正确解码后应该得到相同字符串。它不能修复进入编码器前已经被替换的字符。

## 从一个正则扩展到配置验证

可以把规则验证拆成四层：

1. **结构校验**：字段是否齐全，类型是否正确。
2. **值的回读**：关键配置是否与提交前一致。
3. **行为样例**：一条应该通过，一条应该拒绝。
4. **业务结果**：有效行、错误行与最终发布结果是否符合预期。

对 SQL 模板、路径、Unicode 标识符和复杂过滤条件，也可以采用相同思路。不要只观察“系统有没有报错”，还要核对它是否执行了原来要表达的规则。
