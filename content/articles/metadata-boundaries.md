## 先分清项目的完成度

`deep-agent` 的目录已经包含 MySQL、Qdrant 和 Elasticsearch 的客户端、模型与仓储。仅从名字看，容易以为一套完整的数据问答知识库已经就绪。

但实际读取后，`MetaKnowledgeService.build()` 目前只记录一条日志；字段向量仓储与字段值全文仓储也只保存客户端引用。**这篇文章把它当作架构学习笔记，而不是已完成的产品实现。**

## 三种数据，各自解决不同问题

从服务构造函数的依赖可以看出，它计划接收数据仓库、元数据库、字段值全文索引、字段向量索引、指标向量索引和 embedding 客户端。

按照这些命名，能够整理出一个待实现的职责划分：

| 数据 | 计划承载位置 | 主要用途 |
| --- | --- | --- |
| 表、字段、指标定义 | MySQL 元数据仓储 | 保存结构与关联关系 |
| 字段和指标的语义表示 | Qdrant | 按问题语义找到候选字段或指标 |
| 字段值索引 | Elasticsearch | 对名称、枚举值等做文本匹配 |
| 业务事实数据 | 数据仓库 | 执行最终受约束的数据查询 |

表中是从接口依赖推导的设计意图，不能据此宣称索引已经建好，或 SQL 已经能正确生成。

## 为什么元数据不能只存一段描述

自然语言中的“销售额”可能对应多个指标：含税还是不含税，按下单还是支付时间，退款是否扣除。只召回一个相似字段名，不足以确定口径。

因此，后续实现需要保存稳定 ID、数据源、表与列、类型、业务含义、指标口径和更新时间。向量索引可以帮助找候选，结构化元数据负责把候选约束回可执行对象。

```json
{
  "field_id": "orders.net_amount",
  "table": "orders",
  "column": "net_amount",
  "data_type": "decimal",
  "description": "订单净额",
  "definition": "示意口径，实际以业务定义为准",
  "schema_version": "v1"
}
```

这是建议的数据契约，不是当前仓库中已经实现的模型。

## 从骨架走向可用，需要哪些闭环

建议先实现一条最小构建链：读取结构化元数据，规范化字段标识，生成向量，写入索引，再按 ID 回查校验。全文字段值索引可以作为另一条明确的管线，避免把所有构建逻辑塞进一个巨大函数。

接着处理更新：字段删除之后，旧向量如何失效；同一字段重建是否产生重复；描述修改后如何找到对应的索引记录。若缺少稳定 ID，后续删除和版本对齐会变得困难。

最后才是检索侧：候选召回、置信度不足时的澄清、字段合法性检查，以及查询执行权限。模型生成 SQL 与允许执行 SQL，需要独立判断。

## 一个合理的首批验证集

- 两个同名字段属于不同表，结果应保留所属表。
- 一个指标有两个口径，系统应要求确认或展示差异。
- 元数据字段被删除，旧索引不应继续作为有效证据。
- 某批向量化失败，构建状态应明确报告部分失败。
- 重复构建相同输入，逻辑对象数量不应无故增长。

先把这些可检查的行为写清楚，才能判断代码增加的是目录数量，还是实际可用能力。当前文章提供的是实现路线与边界说明，不把规划伪装成项目成绩。
