## 从两个入口理解 RAG

阅读知识库代码时，先分清两个时间尺度。导入流程处理文件、文本和向量，通常在资料更新时运行；查询流程处理用户问题，必须从已有索引中找到可用证据。把两者放在同一条请求链路里，很容易把解析成本和检索延迟混为一谈。

[RAG-KnowledgeBase](https://github.com/xiaocha653830-tech/RAG-KnowledgeBase) 正好将这两部分拆开：导入图使用 `ImportGraphState`，查询图使用 `QueryGraphState`。**两张图通过持久化知识库衔接，并不共享同一个运行时 State 对象。** 这是核对旧文章草稿时首先需要修正的地方。

## 导入图：七个节点，一条内容加工链

导入图注册了七个节点。入口根据 Markdown 和 PDF 标记选择路径，之后依次处理图片、切分、主体识别、向量化与 Milvus 写入。

```text
文件入口
  ├─ Markdown ─────────┐
  └─ PDF → 转 Markdown ┤
                       ↓
图片处理 → 文档切分 → 主体识别 → 向量化 → Milvus
```

对应的代码位于 `import_process/agent/main_graph.py:21–68`。入口条件函数先检查 Markdown 标记，再检查 PDF 标记；两者都未命中时返回 `END`。这描述的是当前实现，不代表输入校验已经足够完备。

State 中比较重要的字段，可以按职责而不是按声明顺序阅读：

| 职责 | 字段 | 阅读时要问的问题 |
| --- | --- | --- |
| 追踪 | `task_id` | 能否定位一次导入？ |
| 路由 | `is_md_read_enabled`、`is_pdf_read_enabled` | 标记由谁设置，是否互斥？ |
| 文件 | `local_file_path`、`md_path` | 下游读的是原始文件还是处理产物？ |
| 内容 | `md_content`、`chunks`、`item_name` | 元数据是否跟着内容一起传递？ |

如果图片处理改写了 Markdown 路径，切分节点仍然读取旧路径，就会出现“前一步成功，后一步读不到新内容”的问题。理解图，不只是看节点之间的箭头，还要看每条边上传递的数据。

## 查询图：当前版本已经是四路

旧草稿描述三路召回，当前代码还注册了 `node_query_kg`，因此实际分叉是四路：

```text
商品确认
  ├─ 已有 answer → 输出
  └─ 多路搜索
       ├─ 普通向量
       ├─ HyDE
       ├─ Web 搜索
       └─ 知识图谱
          ↓ node_join
       RRF → Rerank → 答案输出
```

查询图包含十个注册节点，其中两个是组织流程的中转节点。这个数字只对应本次读取的本地版本，不应作为项目永久不变的属性。

`route_after_item_confirm` 检查 `answer` 是否已经存在。如果前面的节点决定澄清或拒答，后续检索会被跳过。把短路逻辑放在图中，读代码时就能直接看到哪些成本可以避免。

## 图上有边，不等于数据被消费

`node_join` 返回空字典，表示它不新增状态字段。后面的 RRF 节点只读取 `embedding_chunks` 和 `hyde_embedding_chunks`；Web 结果在重排节点才被合并。知识图谱分支虽然出现在图里，但不能据此推断它参与了 RRF 或最终答案。

排查这类流程时，建议画两张表：一张列控制流，另一张列字段的生产者与消费者。两者不一致的地方，往往就是解释不清或功能未接通的地方。

## 拆成节点，不自动获得断点恢复

这两张图调用的是不带 checkpointer 的 `compile()`。因此，不能仅凭“图由独立节点组成”，就宣称进程重启后可以自动从失败节点恢复。

真正的恢复能力还需要状态持久化、稳定的任务标识、外部副作用的幂等处理，以及失败后的恢复入口。本篇完成的是源码结构核对，没有启动模型、数据库或完整工作流。

## 一份可复用的阅读顺序

1. 找到图的构建入口，确认注册了哪些节点。
2. 阅读条件边，找出提前结束与分叉条件。
3. 对照 State，标注关键字段由谁写入、谁读取。
4. 跟踪持久化边界，区分内存数据与外部存储。
5. 最后检查异常分支和恢复机制，避免从模块拆分推导运行保证。

先建立这张地图，再深入单个模型调用，比从某个长函数一路读下去更容易理解系统。
