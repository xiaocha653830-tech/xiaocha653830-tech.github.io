## 切片的输出应该是一个契约

“把长文档切小”只说明了操作，没有说明结果应该满足什么条件。在 RAG 中，一条切片既是检索对象，也是引用与排障的最小单位。除了正文，它还需要携带来源、标题和所属分段。

本地切分节点采用两阶段策略：先按 Markdown 标题划分章节，再用 `RecursiveCharacterTextSplitter` 处理过长章节。这个顺序可以保留结构信息，但仍有边界需要核查。

## 第一阶段：区分标题与代码

`step_2_split_by_title` 用正则识别一到六级标题，同时维护 `is_code_block` 标记。遇到代码围栏时切换状态，在围栏内不把 `#` 开头的行当作标题。

这个处理很实用，因为 Python 注释、Shell 注释和 Markdown 示例都可能以 `#` 开头。如果只用标题正则，代码示例会被错误地切成章节。

不过，当前实现每行调用 `strip()`，会丢失行首缩进。它适合部分自然语言资料，直接用于技术代码文档时则需要谨慎：Python 代码的缩进本身就是语义。更完整的解析应保留原始行，围栏识别与标题判断使用单独的视图。

## 第二阶段：控制长度并保留上下文

当前节点把章节交给递归切分器，并为子块保存：

```json
{
  "title": "章节标题_1",
  "content": "这一块的正文",
  "parent_title": "章节标题",
  "file_title": "原始文档名称",
  "part": 1
}
```

这是按源码字段归纳的结构示意。`part` 在每个父章节内重新编号，不能单独充当全库唯一标识。

切分器的长度限制还取决于分隔符配置。本地代码使用换行、中文标点和空格，但没有最后的空字符串兜底。因此，不含这些分隔符的超长文本，需要专门检查，不能只看 `chunk_size` 参数就认定所有输出都严格小于阈值。

下面是面向普通文本的改进示例，数值用于演示，不是经过评测的最优配置：

```python
from langchain_text_splitters import RecursiveCharacterTextSplitter

splitter = RecursiveCharacterTextSplitter(
    chunk_size=600,
    chunk_overlap=80,
    length_function=len,
    separators=["\n\n", "\n", "。", "！", "；", " ", ""],
)
```

按字符计数与按模型 token 计数是两种约束。要控制模型输入上限，应使用目标模型对应的分词器测量，而不是套用固定的“中文字与 token 换算比例”。

## 向量化之后，不能只数切片数量

`node_bge_embedding.py` 在批次异常或向量结果为空时，会把原始切片追加到输出。这保留了文本，但这些对象可能没有 `dense_vector` 和 `sparse_vector`。

于是两个看似相近的检查，回答的是不同问题：

| 检查 | 能说明什么 | 不能说明什么 |
| --- | --- | --- |
| 输入与输出条数一致 | 文本对象没有因该分支被丢弃 | 每条都完成了向量化 |
| 所有对象有向量字段 | 必要字段存在 | 维度、数值和索引写入一定正确 |
| 数据库写入成功 | 写操作返回成功 | 检索质量达到要求 |

建议在入库前增加明确的结果校验，把失败批次记录为可重试任务。以下是字段级检查示例，还需要结合实际向量类型扩展：

```python
def incomplete_chunks(chunks):
    required = {"dense_vector", "sparse_vector"}
    return [
        index
        for index, chunk in enumerate(chunks)
        if not required.issubset(chunk)
    ]
```

## 为切分准备有针对性的样例

比起只用一篇正常文档，以下输入更能暴露问题：

- 首个标题之前有导言的 Markdown，检查导言是否保留。
- 含缩进代码和 `#` 注释的章节，检查代码语义。
- 超长 URL、连续字符或缺少空格的文本，检查长度上限。
- 相同章节标题反复出现的文档，检查引用标识。
- 向量模型某一批次失败，检查是否阻止不完整数据进入后续流程。

切片质量不能仅凭数量判断。让每个阶段清楚地说明“输入是什么、输出保证什么、失败留下什么”，才能把切分参数变成可验证的工程行为。
