## 从“数据库写完了，消息没发出去”开始

创建一个后台作业通常涉及两个系统：数据库记录运行事实，消息队列通知 Worker 执行。如果两步独立进行，进程可能在中间崩溃，留下已经创建、却永远没有被调度的任务。

ETL-Agent 的 Commit 服务把运行记录与 Outbox 事件放在同一个数据库事务内提交。它先确保“有一个待执行事实”，再由分发器处理消息投递。

## Outbox 管理投递意图

`commit_preparation` 在添加运行记录之后调用 `enqueue`，最后统一提交。`execution_run_key` 使用运行 ID 构造稳定键，避免把同一逻辑运行误当成多个新事件。

```text
API 事务：运行记录 + Outbox 事件 → 一起提交
                                      ↓
分发器：读取到期事件 → 投递 Celery → 标记已投递
                                      ↓
Worker：条件认领 → 执行 → 带守卫写终态
```

分发器按 `available_at` 取到期事件。失败时增加尝试次数，并按有上限的指数退避推迟下一次执行；重试耗尽后标记失败。这个状态必须被维护任务或运维界面看见，不能把“有重试”表述为“最终一定成功”。

## 投递与标记之间仍然有重复窗口

消息已经发出，但数据库还没记录成功时，进程可能退出。下一轮扫描会再次投递同一个事件。

因此，Outbox 本身不提供端到端“恰好一次”。消费者需要处理重复投递，外部系统的副作用也要有自己的幂等机制。

本地 `claim_run` 用带状态条件的 UPDATE 认领运行。两个 Worker 同时竞争时，只有符合条件的更新能够影响目标行。`rowcount` 是判断认领是否成功的依据，不能先 SELECT 再假设自己的结果仍然有效。

## fencing 防止旧 Worker 改写新结果

Worker 失联后可能被接管，但旧进程并不一定真正退出。它恢复后继续写终态，就可能覆盖新 Worker 的结果。

项目中的 `fenced_update` 把运行 ID、运行状态与租约持有者写入同一条 UPDATE 的条件。这相当于把“我仍有资格写”与“实际写入”合并。

```sql
-- 按本地实现简化的 SQL 示意
UPDATE execution_runs
SET status = 'succeeded'
WHERE id = :run_id
  AND status = 'running'
  AND worker_lease_owner = :worker_id;
```

如果影响行数不是 1，调用方就必须停止按成功路径推进。当前辅助函数在守卫失败时回滚；成功时把提交权留给上层，便于把终态与事件记录一起落定。

## 租约过期与租约易主不是同一个条件

这套实现的终态写入守卫检查持有者，不直接用时间是否过期判定。过期回收由维护任务处理；回收时还比较先前观察到的到期时间，避免与刚完成续期的 Worker 冲突。

这是一种具体的工程约定。它保护的是相应数据库更新，不能直接推出所有外部数据面操作也获得相同保护。外部提交、取消、发布仍需要检查它们各自的授权和幂等边界。

## 有用的故障注入位置

| 故障位置 | 应检查的行为 |
| --- | --- |
| API 提交前失败 | 运行与事件一起回滚 |
| 消息发出后、标记前失败 | 允许重复投递，但重复认领不应推进 |
| Worker 长时间无心跳 | 能回收，且回收不能覆盖刚续期的租约 |
| 旧 Worker 恢复 | 旧持有者不能写入终态 |
| 持续投递失败 | 重试耗尽可见，有明确后续处理 |

这些是建议验证场景。本篇只核对控制面代码，没有重跑消息队列、SeaTunnel 或真实数据库，因此不沿用 README 中的历史测试数量作为本次验收结果。
