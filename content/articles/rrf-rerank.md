## 先回答：究竟融合了什么

笔记中曾留下一个问题：网络搜索是否参与 RRF 融合？只看查询图，多个分支都汇聚在一起；只看概述，又容易把“多路召回”理解成“所有结果使用同一种融合”。

当前本地实现给出的答案很明确：`node_rrf` 只读取普通向量检索和 HyDE 检索的结果。Web 结果由 `node_rerank` 另外取出，随后一起送入重排模型。这是本项目当前的实现选择，不是 RRF 算法的固有限制。

## RRF 使用名次，不直接比较原始分数

本地节点对两路结果各赋予 `1.0` 的权重，调用 `step_2_rrf(..., k=60, max_results=None)`。这意味着旧草稿中的“RRF 固定最多十条”不能直接套用到当前版本。

RRF 的核心可以写成：

```text
score(document) = Σ weight_i / (k + rank_i(document))
```

排名从 1 开始。在两个榜单中都靠前的文档会得到多次贡献；只出现在一路中的文档也可以保留。

下面是独立的算法演示，使用文档 ID 去重，不依赖项目运行环境：

```python
def rrf(rankings, k=60):
    scores = {}
    for ranking in rankings:
        # 同一榜单内重复 ID 只贡献一次
        unique_ids = dict.fromkeys(ranking)
        for rank, doc_id in enumerate(unique_ids, start=1):
            scores[doc_id] = scores.get(doc_id, 0.0) + 1 / (k + rank)
    return sorted(scores.items(), key=lambda item: (-item[1], item[0]))

print(rrf([["a", "b", "c"], ["b", "d", "a"]]))
```

RRF 本来就可以用于不同检索方式得到的有序列表。跨源使用时，需要定义文档身份、重复文档的对应关系和缺失结果的处理方式；不能简单断言“网络文档不能参与 RRF”。算法说明可参考 [Microsoft 的 RRF 排名文档](https://learn.microsoft.com/en-us/azure/search/hybrid-search-ranking)。

## Web 结果在重排阶段进入

`step_1_merge_docs` 将本地切片转换为带 `text`、`doc_id`、`title`、`source` 的对象，再将 Web 的摘要、标题和 URL 加入同一个候选列表。

| 来源 | 正文来源 | 追踪字段 |
| --- | --- | --- |
| 本地切片 | `content` | `chunk_id` / `doc_id` |
| Web 搜索 | `snippet` 或 `content` | `url` |

随后以改写后的查询为优先输入，为每个候选构造查询—文本对，调用 reranker 打分，再按得分降序排序。

这种组织方式把两件事分开：RRF 合并已有排名；reranker 对候选文本重新计算相关性。两层都有价值，但它们回答的问题不同。

## 动态截断如何工作

当前重排代码在配置的上下界内扫描相邻分数。绝对差值或相对差值达到阈值时，就在该位置截断。相对差值的分母使用前一分数的绝对值，再加一个很小的数避免除零。

这是一种启发式策略。它能响应分数曲线的变化，但分差不是可靠性的证明，更不是答案正确率。不同模型、不同查询类型，可能需要分别校准阈值。

还要注意异常分支：模型打分失败时，代码把候选得分设为零后返回。此时后续结果并没有经过有效的模型排序。接口或日志应能区分“重排成功”和“降级保留候选”。

## 怎么验证这条链路

建议为每个问题保存四份中间结果：原始召回列表、融合列表、重排分数和最终引用。这样才能判断错误发生在召回、融合、截断还是回答阶段。

本篇核对了数据消费关系与函数实现，未运行检索基准。没有标注数据集时，不将某个权重、阈值或候选条数描述为最优值。
