两个子任务已经同时发出，用户却要等八分多钟才能拿到旅行方案。

这是我做 DeepAgent 旅行助手时遇到的问题。项目接了高德和 12306 两个 MCP 服务，分别处理地图与票务信息。我最初和 DeepSeek 抱怨，任务耗时久，token 花费多，生成的内容还又多又杂。

讨论很快转向并行。DeepSeek 建议修改主代理的提示词，让地图和票务子代理同时工作。但我去看 LangSmith，发现原来的两个 `task` 就已经同时发出了。

后来回到这次武汉到北京两日游的运行记录，等待才有了更具体的轮廓。

接下来值得追问的，是地图子任务接到了多大的工作，以及查完以后为什么还需要那么久。

## 地图助手接到的，已经是一份完整攻略

主代理交给 `map_agent` 的指令，比“查几个景点的交通路线”展开了很多。

它要求从一批经典景点中覆盖 6—8 个，查询位置、开放情况、门票与预约信息，再安排两天的景点顺序。交通部分既要查景点之间的路线，也要考虑北京西站、北京南站、北京丰台站到酒店区域或首站景点的接驳。最后还要补天气，交付一个推荐方案和一个备选方案。

![地图子任务的派发参数、内部调用与攻略输出](./assets/deepagent/map-task.png)

*图 2　展开 371.72 秒的任务，可以看到 `task` 派发给了 `map_agent`，返回内容已经是一份景点与市内交通方案。*

其中有些工作确实能帮助规划，但它们都要付出查询和判断成本。尤其在车次和到站位置还没确定时，同时研究多个车站的接驳，就会提前展开一些最后未必用得上的路线。

工具调用记录也呈现出几个阶段。子代理先查询景点和天气，随后获取 POI 详情，再解析车站等地点的位置，准备查询关键交通路线。这里有些先后顺序有实际原因。地点搜索返回的字段不够时，需要继续拿到坐标，才能计算路线，不能把所有后续调用都算成多余工作。

但查询范围可以更早收敛。先选出本次两日游真正需要的少量候选，再详细查相关地点；确定候选车站以后，再查对应接驳。需要比较多个车站时，也应当让比较服务于选车次，而非默认替所有车站各做一份完整方案。

这一步调整的是任务本身。只在原指令后面加一句“请并行执行”，这些工作仍然都要有人完成。

## 同时开始，也要等较慢的任务结束

把这次运行想成两个人一起准备旅行资料，就容易理解剩下的等待了。

一个人查车票，另一个人查地图。两个人同时开始，确实可以省掉排队的时间。但如果完整行程需要两份资料，就仍然要等较慢的那个人。地图这边花了六分多钟，另一边即使先完成，最终方案也不能因此提前齐备。两份资料到齐之后，整理报告又是后面的一段工作。

这也能帮助理解[阿姆达尔定律](https://www3.cs.stonybrook.edu/~rezaul/Spring-2012/CSE613/reading/Amdahl-1967.pdf)的提醒。固定任务里，那些必须按顺序完成的部分，会限制增加并行带来的提速。至于哪个并行分支拖到最后，还要具体看每条分支做了多久。本文不需要用公式计算上限，先找出用户还在等哪件事，就能决定下一步查哪里。

异步子代理解决的是另一项等待。按 [Deep Agents 的文档](https://docs.langchain.com/oss/python/deepagents/async-subagents)，同步子代理可以并行执行，同时让主代理等待结果；异步子代理则允许主代理派发后继续工作，之后再取结果。

这对中途响应用户和调整任务有价值。不过，只要最终行程依赖地图结果，地图没有查完，这份行程仍然没有完成。把任务搬到后台，或者部署到另一台机器，都不会自动缩短其中的查询与模型调用。

## 高德已经返回限流，继续加并发未必合适

这次工具返回里，出现了一条比“感觉接口慢”更具体的线索。

`maps_text_search` 返回过 `Text Search failed: CUQPS_HAS_EXCEEDED_THE_LIMIT`，`maps_search_detail` 也返回过同类限制信息。这证明这次执行中发生了限流。

因此，优化还要检查请求发出的节奏。并发适合让互不依赖的工作一起执行，但外部服务能够接住多少请求，是另一项约束。把更多请求挤到同一时刻，可能只会得到更多失败结果，随后又要花时间处理失败。

可以在调用层限制同一服务的并发和请求频率。遇到限流时，按规则等待后有限重试；仍然失败，就返回已取得的数据和明确缺口。限制需要由程序执行，提示词里的“不要重试太多次”无法代替它。

不过，这条错误还不足以解释全部六分钟。当前没有逐个核算所有请求的耗时和重试过程，不能把限流直接写成唯一原因，也没有证据说子代理陷入了无限循环。文章能够确认到的地方，是限流已经发生，请求调度需要考虑服务容量。

## 多接几个 MCP，不必再多套几层代理

聊到单个子代理耗时，我担心继续拆子代理会增加更多模型调用。DeepSeek 随后建议把地图与票务工具直接交给主代理，我又提出了未来的约束。现在只有两个 MCP 服务，后面可能接十几个甚至更多。

这个问题需要同时看执行轮次和上下文。把工具全放到主代理，可能省掉委派，却让主代理面对更多工具定义和业务规则。每个服务各配一个子代理，又可能增加本来不需要的模型决策。

比较适合继续验证的方向，是保留地图、票务等业务入口，把内部已经确定的步骤交给代码。地点已经选好，按 POI ID 取详情、核对城市、筛掉无关字段，可以走固定流程；要在多个景点组合间作出选择，再让模型参与。[LangGraph 对工作流与 Agent 的区分](https://docs.langchain.com/oss/python/langgraph/workflows-agents)也允许这种结合，固定处理与动态判断可以放在同一个业务流程里。

这样，拆分工作不必对应更多代理。模型负责需要理解和取舍的部分，程序负责明确的查询与校验，也就少了一些“解释任务、重新理解、再整理一次”的往返。

服务增加时，还可以收窄当前模型能看到的工具。[LangChain 的上下文工程文档](https://docs.langchain.com/oss/python/langchain/context-engineering#selecting-tools)提供了动态选择工具的机制。是否需要独立子代理，则要看领域知识、工具规模与上下文隔离的收益，[多代理文档](https://docs.langchain.com/oss/python/langchain/multi-agent/index)也把这些列为选型依据。单凭 MCP 的数量，还不能决定代理应该有几层。

## 数据进来以后，模型还在处理什么

等待之外，我最初提到的“内容又多又杂”，在工具返回里也能找到具体例子。

一次故宫搜索，除了故宫博物院，还返回了检票处、午门、角楼和多个院内建筑，许多条目带着照片链接、分类代码和空字段。天气查询也返回了多个日期，以及重复表示的温度。两日游真正需要的，只是选定景点的必要信息和行程日期内的天气，原始响应明显超出了这个范围。

这些内容全部进入上下文，模型就要先从大量候选中挑选，再判断哪些字段值得保留。工具返回得越多，后续需要阅读和整理的材料也越多。因此，限制应该同时落在查询行为和返回数据上。

提示词可以先约束查询范围与数量。例如，只查询指定城市和日期，先筛出少量符合行程的景点，再查详情，不主动扩展到所有附属地点。对子代理的最终返回，也可以约定候选条数和必要字段，保留地点、POI ID、位置及路线所需信息，避免再附上一整篇攻略。这能减少无关查询和交给主代理的冗余内容。

对于一次就返回大量数据的 MCP 工具，还需要在调用参数或代码里控制体量。工具支持时，设置条数、分页和返回字段；不支持时，在结果进入模型前，按已确定的条件筛选候选，去掉照片链接、空字段和重复数据。只要求模型“最后回答简短”，整份原始响应仍然已经被读入。筛选时也要保留后续规划所需的标识与坐标，避免为了压缩内容又补查一轮。

## 写在最后

这次八分多钟的运行，让最初那个“再加一点并行”的想法有了具体边界。两个子任务同时开始，地图助手仍然要完成一整份攻略研究，处理大量候选和原始字段，期间还遇到了限流。这些已经看到的工作与错误，比代理数量更能帮助判断下一步该改哪里。

对这个旅行助手，值得继续验证的方向是保留地图与票务的业务分工，先收窄每次派发的任务，再控制外部请求的节奏。确定的查询、筛选和校验交给代码，需要理解与取舍的地方再让模型参与。业务扩展时，工具可以按需提供，避免每增加一个服务，就增加一层模型往返。

这些调整能省下多少时间和 token，还需要用相同问题重跑才能回答。核对时既要看等待有没有缩短，也要看景点、车站和时间条件是否仍然正确。少查无关内容、少做重复判断，同时保留规划所需的依据，才是这次分析之后值得检验的改进。
