## 格式转换首先要保留阅读顺序

整理课程文档时，Word 中往往交替出现段落、表格和代码。若先遍历全部段落，再遍历全部表格，内容虽然没有丢失，顺序却已经错了。

项目内的[工具核对笔记](https://github.com/xiaocha653830-tech/xiaocha653830-tech.github.io/blob/main/content/references/docx2md-tools.md)记录了这一做法：转换工具遍历文档 body 的子元素，按顺序识别 `w:p` 与 `w:tbl`。这比简单拼接 `document.paragraphs` 和 `document.tables` 更贴近原始叙述。

```python
# 按本地工具整理的核心片段
def blocks(doc):
    for child in doc.element.body.iterchildren():
        if child.tag == qn("w:p"):
            yield Paragraph(child, doc)
        elif child.tag == qn("w:tbl"):
            yield Table(child, doc)
```

这段覆盖的是顶层段落和表格，不应据此认为所有 Word 布局结构都被完整支持。

## 用样式识别代码，比猜内容更可靠

工具先检查段落样式是否包含代码样式名称，再根据等宽字体字符比例判断。比例达到 `0.85` 时，会把段落视为代码。

识别后，它连续收集代码段，在切换回正文或表格之前关闭围栏。这样的状态机可以避免每行代码都生成一个独立代码块，也保留原始代码行的缩进。

但这是启发式识别：正文可能使用等宽字体，代码也可能缺失统一样式。转换之后仍需要抽查，尤其是代码与普通说明交替出现的位置。

## 表格转换做了哪些取舍

工具将单元格中的多行文字合并，以首行生成 Markdown 表头，再补充分隔行。单元格里的竖线被替换为斜杠，避免破坏 Markdown 表格结构。

这能产生容易阅读的表格，却改变了原始内容表示。若竖线属于代码、逻辑表达式或业务值，就不应静默替换。另一种策略是转义竖线，并明确处理换行和代码片段。

Word 中合并单元格、复杂嵌套或跨页布局，也不一定能无损映射到普通 Markdown 表格。转换的目标应该事先说清楚：保留技术内容结构，还是追求版式还原。

## 标题识别也需要边界测试

现有函数先判断样式名是否含中文“标题”，之后才尝试匹配英文 `heading`。这意味着纯英文 `Heading 1` 样式可能在前面的条件就被排除。

中文级别映射中也存在非常规映射，例如“二”对应 3，需要确认它是否是针对某份模板的有意设计。将工具推广到其他文档前，应把“模板约定”与“通用标题规则”分开。

改进时可以先识别标准英文 Heading，再匹配中文自定义样式，并对无法识别的样式输出提示，避免把标题静默转换成正文。

## 自动质检能做什么

配套的 `qc.py` 统计标题、围栏和表格数量，并检查围栏数是否为偶数。这是有价值的初筛，但偶数不等于配对一定正确：围栏位置可能不对，内容中也可能出现同样的符号。

| 检查层次 | 合适的检查 |
| --- | --- |
| 文件层 | 编码、空文件、转换失败记录 |
| 结构层 | 标题层级、围栏闭合、表格列数 |
| 内容层 | 代码缩进、公式、链接、关键术语 |
| 视觉层 | 抽样渲染长表格、嵌套列表与代码段 |

当前工具会跳过图片样式段落，也没有完整图片资源导出流程。因此它生成的是文本导向的 Markdown，不能描述为保留所有插图的转换器。

## 从资料到文章，还需要编辑

转换出来的 Markdown 是素材，不等于适合直接发布的文章。技术博客还要重新组织问题、实现、取舍和验证方式，并标注来源。课程原文、占位配置与本机路径也需要经过整理。

本博客采用单独的 Markdown 文章与元数据清单维护内容，让资料转换和文章发布成为两步明确的工作。这样后续修改标题、分类和正文，都不需要进入页面渲染函数。
